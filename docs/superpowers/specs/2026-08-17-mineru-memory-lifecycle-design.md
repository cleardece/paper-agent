# MinerU 内存生命周期设计

## 目标

在不降低 MinerU 解析准确性的前提下，避免 PDF 解析完成或失败后继续长期占用大量内存。默认策略应适用于内存和 CPU 配置未知的开源用户；用户保持原有的上传操作，无需手动管理 Docker 容器。

## 已确认的原因

MinerU 以常驻 Docker 服务运行，会保留已加载的模型以加快下一次解析。静止采样中，`mineru-api` 占用约 4.5GB，WSL/Docker 虚拟机仍保留约 11.8GB 私有内存。这不是 Milvus 或 MongoDB 的泄漏，也不应通过降低默认解析器质量来规避。

## 设计

1. 上传任务开始前，应用确认 MinerU 容器已启动；若未启动则启动并等待健康检查通过。
2. 解析任务结束（无论成功或失败）后，如果没有其他解析任务，默认立即停止 MinerU 容器并释放模型内存。
3. 容器停止后，下次上传自动重新启动。第一次解析会有冷启动等待，但仍使用同一套 MinerU pipeline，解析质量不变。
4. 资源策略通过环境变量配置：内存充足、需要连续上传的用户可以选择保留空闲容器；默认不假设固定内存大小，也不强加固定 Docker 内存上限。
5. CPU 使用限制同样是可选配置。默认不因限制 CPU 而降低解析吞吐；资源受限设备可选择限制 MinerU 使用的 CPU 核数，以保持桌面响应。
6. 如果 MinerU 因资源不足或进程故障而无法完成解析，上传状态明确标记为失败；不得把 pdfplumber 的回退结果静默写入高准确性论文库。用户可明确选择普通解析或重试。

## 并发与错误处理

- 使用进程内异步锁和活动任务计数，避免一项任务解析时另一项任务停止容器。
- 启动、停止和健康检查均有明确超时和可读错误信息。
- Docker 不可用时维持现有的普通解析回退能力，但在界面和日志中清晰说明当前结果不是 MinerU 解析。
- 停止容器仅影响 MinerU；MongoDB、Milvus 与其他服务继续运行。

## 配置

- `MINERU_IDLE_SHUTDOWN_SECONDS`：默认 `0`，即单次任务完成后立即释放；可设为正数以保留热启动窗口。
- `MINERU_MEMORY_LIMIT`：可选。未设置时不施加固定上限；部署者可按实际内存设置 Docker 上限。
- `MINERU_CPU_LIMIT`：可选。未设置时不限制；部署者可设置为 CPU 核数或配额以避免桌面卡顿。
- `MINERU_REQUIRE_ACCURATE_PARSE`：默认开启。开启时，MinerU 失败不自动入库 pdfplumber 的结果。

## 验收标准

- 正常上传仍使用 MinerU pipeline，操作方式不变。
- 成功、失败和取消后，默认会立即停止 `mineru-api`；配置了空闲窗口时才延迟停止。
- 停止后 Docker 统计不再包含 MinerU 的约 4.5GB 常驻占用。
- 新上传会自动恢复解析服务。
- 资源配置导致 MinerU 无法完成解析时，用户看到明确失败原因，且不会把低质量回退结果伪装为准确解析结果。
